Overview

Hoarder already captures downloadable media into user-controlled storage and has a small local catalog prototype. The next system makes the mounted files—not downloader history—the durable source of truth, then layers review, evaluation, music derivation, browser image capture, and channel curation on top.

The chosen shape is a single-user service hosted beside the media, exposed as a local browser/PWA over the private network. It uses configurable storage adapters, PostgreSQL, a durable worker queue, a FastAPI-compatible ingest boundary, and a richer web client. Original media remains immutable. Derived artifacts and editorial metadata are independently recoverable.

Product principle: one unified asset catalog, three purpose-built lenses. Video, music, and images share provenance, tags, and collections without being forced into the same browsing experience.

Measured Starting Point

A read-only audit found a working prototype with a catalog API, SQLite database, media tabs, streaming routes, a browser image-upload endpoint, downloader synchronization, and FFmpeg audio extraction. It also found a substantial gap between indexed video rows and paths that resolve to real files.

This validates the product direction but rejects the current ingestion assumption: downloader history is useful metadata, not an authoritative inventory. The first release begins with filesystem reconciliation and explicit storage health.

Goals & Non-goals

Goals

  • Browse every supported file on every configured online root.
  • Retain original source channels and build reusable curated channels.
  • Evaluate with ratings, notes, tags, workflow state, and optional rubrics.
  • Create a properly tagged music library while retaining video provenance.
  • Save original images from the browser into the same catalog.
  • Make failures, offline disks, and missing files explicit and recoverable.

V1 non-goals

  • Multi-user accounts, permissions, or collaboration.
  • Automatic destructive moves or renames of archived originals.
  • Transcription, OCR, semantic embeddings, or face recognition.
  • Continuous channel scheduling, EPG generation, or TV playout.
  • Replacing downloader services or a future movie/TV media server.

Product Lenses

Video

Grid and table browsing, source channels, playback, rapid evaluation, candidate workflow, and curated-channel assignment.

Music

Music candidates, extraction jobs, artist/album/track editing, artwork, playlists, and provenance back to source video.

Images

Browser-saved originals, source pages, dimensions, duplicate detection, tagging, collections, and future slideshow use.

Primary screens

  • Inbox: newly discovered assets and music suggestions awaiting a decision.
  • Videos, Music, Images: media-specific browsing with shared search and filters.
  • Source Channels: original creators, publishers, feeds, and websites.
  • Curated Channels: ordered collections with candidate → reviewed → selected → used state.
  • Asset Detail: player/viewer beside metadata, provenance, evaluation, tags, and memberships.
  • Jobs: current and failed scans, extraction, thumbnails, imports, and retry actions.

Music Derivation Contract

  1. Classifier suggests music from source metadata and detected properties; a user confirms it.
  2. User selects the full program or a time range and chooses archival plus playback outputs.
  3. Worker extracts with FFmpeg to a temporary path, validates with FFprobe, and atomically activates the derivative.
  4. System proposes artist, release, track, artwork, genre, year, and track number without overwriting confirmed metadata.
  5. Reviewed audio becomes a first-class track while retaining source video, URL, channel, timestamps, and extraction recipe.
Default formats: retain a lossless archival derivative when the source warrants it and create a broadly compatible playback derivative. Exact codecs remain configurable rather than embedded in the catalog model.

Failure and Recovery Semantics

  • Every storage root reports online, offline, or degraded.
  • An offline root never causes deletion or “missing” transitions. Only a completed scan of an online root may mark a file missing.
  • Scans use path/size/mtime first and cryptographic hashes when identity is ambiguous.
  • Moves reconnect to the same logical asset. Duplicate copies become multiple asset_files.
  • Worker output is temporary until tool exit, file existence, size, and FFprobe validation all pass.
  • Failed jobs retain stage, safe error summary, attempt count, and retry eligibility.
  • Schema migrations and database backups are versioned and tested with disposable restores.

Risks & Mitigations

RiskSeverityMitigation
Offline removable/network storage is mistaken for deletion.HighSentinel health, three-state root status, and deletion transitions only after a completed online scan.
Prototype history paths contaminate the new catalog.HighImport as untrusted metadata hints; only the storage scanner establishes physical availability.
FFmpeg job damages or replaces an original.HighRead-only original mounts, separate derivative root, temporary output, validation, and atomic rename.
Changing paths loses evaluation and channel work.HighLogical asset identity separated from physical file locations and reconciled through fingerprints.
Rich enrichment stalls delivery of a trustworthy catalog.MediumTranscription, OCR, embeddings, and automated matching are post-v1 modules behind durable jobs.
The prototype remains an unversioned production snowflake.HighPhase 0 creates a clean repository, sanitized configuration, migrations, and reproducible Compose deployment before feature edits.

Verification Gates

  • Inventory: every supported file on an online configured root is cataloged, explicitly quarantined, or reported unsupported.
  • Idempotence: two unchanged scans create zero new logical assets, files, or derivatives.
  • Offline safety: disconnect simulation creates zero deletion or missing transitions.
  • Immutability: before/after checksums for original fixtures are identical across every worker test.
  • Streaming: representative codecs support start, seek, resume, and unavailable-file responses through ID-based routes.
  • Music: full and clipped extraction pass FFprobe; interruption and retry leave exactly one activated derivative.
  • Images: browser context-menu upload preserves original bytes and records source metadata without exposing configuration.
  • Editorial durability: ratings, notes, tags, and memberships survive rescans, moves, service restarts, backup, and restore.
  • Deployment: exact image digests, migrations, health endpoints, database restore, and target-hardware browser proof are recorded separately.

Future Modules After V1

Once catalog identity and editorial state are dependable, enrichment workers can add transcription, chapters, OCR, detected topics, and semantic search. Those outputs remain replaceable derivatives.

The later playout plane will import or reference the household movie/TV collection, compile curated channels into schedules or rules, generate an electronic program guide where useful, and target specific TVs or displays. Scheduling and playback consume the catalog API; they do not redefine asset identity or mutate the archive.

Open Questions

Repository boundary: recommended default is a new hoarder service repository or monorepo, with the browser extension retained as its own releaseable client until a deliberate consolidation is justified.
Frontend stack: recommended default is a typed React PWA backed by the existing Python/FastAPI direction. The API contract remains independent so the UI can change without rescanning media.
Audio formats: choose archival and playback codec defaults during Phase 4 using representative source-quality measurements; keep recipes configurable and versioned.
